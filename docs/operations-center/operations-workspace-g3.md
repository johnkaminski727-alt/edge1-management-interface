# Edge1 Operations Workspace G3 — private multi-module console

**Status:** isolated offline-tested staging branch. Production G1 and G2 remain intact; G3 installation requires separate operator execution of pinned revision.

## What G3 actually adds

G3 combines the existing G2 saved-candidate workspace with a real, read-only Edge1 operations view. The browser now has **Overview, Services, Network, Security, Candidate settings, and Audit & ToolBox** sections. It preserves G2's existing local candidate database and private authentication token: it does not create a new identity system, new monitoring service, second candidate store, or production Apply operation.

A separate non-privileged `tools/operations/edge1_host_metrics.py` reads the operating system's `/proc/loadavg`, `/proc/meminfo`, `/proc/uptime` and root-filesystem `statvfs` summaries on authenticated G3 requests. It provides 1-minute CPU load (not CPU percentage), core count, memory used/available, root filesystem used/available and uptime. Values are strictly bounded and do not include process lists, mount inventories, usernames or environment data. Host-resource freshness is request-time only, while network/security observations have independent publication timestamps.

A new pure `tools/operations/edge1_operations_view.py` reads **existing** on-host `core-status.json` and `network-defense/data/network-defense.json` generated by the established Edge1 collectors. It requires the core snapshot's known schema, read-only and no-mutation flags and requires the network-defense snapshot's no-mutation flag, component and source maps. It independently evaluates freshness (five-minute maximum, one-minute future tolerance) and emits only explicitly allowed service states, interface UP/availability, IPv4/IPv6 forwarding flags, curated security component states and a few numerical counts. Missing/invalid/stale data is marked unavailable or stale; **stale statistics cannot be presented as currently healthy**. Individual IPs, routes, private tunnel peers, command output, attack payloads, credentials and raw firewall rules are never relayed by the G3 operations endpoint.

`tools/operations/edge1_operations_api.py` reuses G2's private single-user token, Host/Origin protections, transactional candidate store and existing endpoints. It adds `GET /api/operations`, authenticated just like `/api/state` and `/api/audit`. It binds exclusively to `127.0.0.1`, defaults to port `8769` and has no Apply, service restart or firewall commands. It runs only while the operator explicitly starts it over an SSH-forwarded session. No persistent service is installed.

The new HTML reuses G2's candidate edit workflow and adds multi-tab operational cards that use DOM `textContent` instead of injecting untrusted observation fields as HTML. It has no unprotected raw snapshot endpoint; login token stays only in the active browser tab's memory.

## Honest capability boundary

G3 shows service/interface observations, sanitized Network Defense posture and bounded live host load/memory/root-disk/uptime metrics; it does **not** yet deliver full CPU utilization trends, arbitrary peer/address lists, interactive diagnostics, production running configuration, editable firewall/DNS/routing rules or authenticated multi-user RBAC. Service-active does not imply external reachability; an observed firewall chain does not guarantee comprehensive traffic filtering. The Spamhaus guarded boot rollback proposal remains a separate unfinished draft.

The browser's "running" display settings remain the G2 **demonstration baseline**. Candidate changes persist only in the G2 SQLite store. Any future production setting read/apply needs separate source authenticity, snapshot versioning, authorization, protected audit, staged approval, recovery checkpoints and rollback tests.

## Proposed opt-in installation and private access

The G3 installer `deploy/candidate-workspace/install-g3.sh` has default check-only mode and, with explicit operator execution via sudo from `wwadmin`, installs a new isolated read-only code package at `/opt/edge1-operations-workspace-g3`. It verifies the existing G2 private data/token, **does not change** `/opt/edge1-candidate-workspace-g2` or `/var/lib/edge1-candidate-workspace-g2`, and does not create a network listener. Upgrades to recognized G3 installations back up the prior G3 code package only. Installation must use a pinned Git commit, isolated `git archive`, local `--check`, `--apply`, `--verify` and complete terminal evidence; do not switch the production repository main branch.

To start an optional G3 private browser session, run on **Windows PowerShell** after verified installation:

```powershell
ssh -L 8769:127.0.0.1:8769 edge1 "python3 /opt/edge1-operations-workspace-g3/edge1_operations_api.py --ui /opt/edge1-operations-workspace-g3/index.html --database /var/lib/edge1-candidate-workspace-g2/candidate.sqlite --token-file /var/lib/edge1-candidate-workspace-g2/access-token --port 8769"
```

Keep PowerShell open while using `http://127.0.0.1:8769/`. Sign in with the **existing G2 private token**, which should be retrieved only in the user's authenticated Edge1 SSH shell and **never shared in chat, logs or screenshots**. If the port is occupied, inspect the existing local listener before starting another copy; do not kill production processes blindly. Ctrl+C stops this temporary preview server.

## G3 test and release gates

`tests/validate_edge1_operations_g3.py` uses temporary fixtures to verify precise whitelisted fields, redaction of secrets/addresses/peer identities, stale data fail-closed, invalid safety-contract rejection, symlink refusal, token-protected G3 API and unchanged G2 candidate routes. Existing G1 validator, G2 persistence and G2 HTTP integration suites must also pass. CI runs shell syntax, `--check` installer preflight, Python and browser syntax tests; it does not perform the privileged install or claim Edge1 live operational freshness.

Follow-on G4: sampled CPU/memory/disk history using an explicit sanitized collector contract, bounded inventory search and real candidate source-of-truth snapshots; after that consider audited multi-user authorization and permissioned apply jobs. Avoid exposing raw system snapshots publicly or guessing unavailable telemetry.
